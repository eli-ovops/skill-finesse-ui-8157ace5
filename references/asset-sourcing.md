# Image sourcing: accountable assets within the current authorization

Load when images matter to the requested interface. Preserve real-product identity, provenance, licensing, privacy, and the agreed image scope; do not turn every page into an image-generation task.

## 0. Decide what the brief actually needs

Use supplied real assets first when the brief depicts a specific product, place, or person. Identify useful image slots and their subjects rather than silently replacing required photography with a gradient. If no imagery is useful, proceed without it.

Current explicit authorization for the same source, subjects, purpose, and cost is sufficient; do not require an additional yes for each image or batch. A vague aesthetic preference alone does not authorize spending, a sensitive upload, new external services, or replacing a real product with invented imagery. Ask only for a missing decision that materially affects cost, privacy, provenance, or the agreed result, and continue independent work. Silence is not missing approval.

## 1. Choose an available, appropriate path

1. Reuse authorized project/CMS/DAM assets when they represent the intended subject.
2. Use an actually available generation tool if the requested result and current authorization cover it.
3. Use suitable licensed public imagery when its source, retrieval, privacy effects, and usage fit the task.
4. If no permitted source meets the need, state the gap. A labelled candidate placeholder can support layout, but does not complete an imagery-dependent deliverable.

Use the session's actual tool documentation and current evidence. Listed capability is not a successful call; do not promise verified generation or image loading before observing it. Do not inspect credentials, request secrets, install a backend, or consume generation budget solely as a speculative preflight. A native image tool may use the platform session; a CLI may require separate setup, so do not generalize one path's requirements to all hosts.

If the chosen path fails, check the supported blocker guidance and current evidence. Choose an already-authorized alternative that preserves the result; ask about material changes. Do not bypass a network denial by hotlinking the same blocked destination through a user's browser. Unverified external image loading stays unverified.

## 2. Generated imagery

- Plan the useful shot list: subject, framing, lighting, aspect ratio, and how it fits the layout. Keep color/lighting consistent across the page.
- Use existing explicit image authorization; obtain a concrete decision only for uncovered fees, sensitive data, a changed subject/source, or a material scope increase. A required unanswered approval remains pending.
- Never present generated imagery as a real photograph of a specific product, location, customer, or event without the corresponding factual basis.
- Preserve real product geometry and applicable photo/3D evidence. Read the relevant product-image workflow for fidelity-critical work.
- Never generate identifiable real people under this Skill; use an authorized real photo or an anonymous/stylized subject.
- Alt text describes what is actually depicted and does not fabricate a photographer, customer endorsement, or location.

## 3. Licensed public imagery

- Choose specific images, inspect them, and retain the actual source/license evidence. Do not fabricate asset URLs or use random-image endpoints whose content changes on reload.
- A public URL or a free label does not prove reuse rights. Check the applicable current license and conditions; do not assume all stock sites or assets share one license.
- Use stable delivery appropriate to the project: authorized local files or verified remote URLs. Consider responsive crops, performance, and the privacy impact of third-party loading.
- Do not scrape a restricted source, bypass a block, or imply that a stock subject endorses the user's product.
- If hotlinks fail or are slow, verify the failure and use a local copy only when the source/license and existing scope permit it. Announce the meaningful change; ask only when the alternative needs new authority or materially changes delivery.

## 4. Explicit candidate placeholders

If no permitted source is available, an original CSS/Canvas texture or neutral composition can validate layout. Label it as a temporary candidate substitute and retain the missing image requirement; do not silently declare the task complete. Do not use a generic placeholder to stand in for a known real product's identity.

## 5. Validate and report

- Keep one coherent grade, lighting language, and crop logic unless the brief calls for a deliberate change.
- Preserve source/provenance and honest alt text. No invented customer portraits, endorsements, or visual claims.
- Use responsive images, appropriate formats, sizes, and below-the-fold lazy loading.
- Inspect actual asset loading and relevant desktop/mobile crops when authorized tools are available; static markup is not proof that a remote photo loads.
- Report the source and actual verification layer, plus unresolved rights, access, or rendering gaps. Approval, a proposed shot list, generation, and accepted final imagery are distinct states.
